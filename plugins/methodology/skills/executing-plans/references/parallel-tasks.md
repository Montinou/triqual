### Parallel tasks

Independent tasks of one phase are built at the same time: the orchestrator runs them (the main session, in the fallback). One of them works in the main checkout and each other one in its own git worktree, and the worktree tasks land on the phase branch in plan order. Nothing runs in parallel across phases, and a phase whose tasks each depend on the one before runs exactly as before. Parallel runs need store or local tracking mode: in committed mode every worktree commit would append to `progress.md` and `status.md` and the landings would conflict, so `stack.mjs init` refuses committed mode before Task 1 (see Stack setup).

**Independent.** A task is independent when every task it depends on is complete and its plan `**Files:**` paths share no path with any earlier task of the phase that is not yet closed, running or not yet started (a task is running from its `task-open` until its `task-close`): an earlier task that overlaps it always starts first. The reason is the landing order: if a later task ran while an earlier task it overlaps had not started, the earlier would wait for the later to close, and the later `task-close` waits for the earlier to land: a deadlock. A task that is not independent runs sequentially: it starts once that earlier task is closed. A path a plan forgot to list is caught by the landing, below, never guessed. **At most 3 implementers at once**, the one in the main checkout included, and a fix round's implementer or fixer counts as its task's. A fix round that is due while all 3 slots are busy waits for the first implementer to report, ahead of any task that has not started; a fourth independent task likewise waits until one of them has reported. The reviewers of a finished task are not counted. Batched light tasks never run in parallel: a batch (see Batched light dispatch) is one implementer working one task at a time, so no other task runs while a batch's task does, and none of a batch starts while another task runs. **An earlier task is never blocked by a later one.** A later task never starts while an earlier task that has not started could be held back by it: a batched light task holds back every other task, so a task of a batch starts only when every earlier task of the phase is closed (a batch therefore always runs in the main checkout); a parallel task holds an earlier one back only through a shared path (the independence rule above) or a slot (the slot rule above), and both are ruled out there. Otherwise an earlier task that has not started, with a light task started first, would wait for the light task to close while the light task's `task-close` waits for it to land.

**Where.** A task uses the main checkout only when every earlier task of the phase is done or dropped; every other task is opened with `node scripts/task-open PLAN_FILE N --worktree`. That makes `.claude/worktrees/<plan stem>-t<N>` on the branch `wt/<plan stem>-t<N>`, started at its BASE, adds `.claude/worktrees/` to `.git/info/exclude` once, and installs from the worktree's lockfile (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile`; no lockfile, no install): a failed install is exit 1 with an `Error:` line. The BASE of a worktree task is the last closed commit of the phase branch: the phase tip, or, when a task built in the main checkout has commits that no `task-close` has squashed yet, that task's own BASE, so the worktree task is never based on, nor reviewed with, commits nobody has reviewed. It prints `workdir:` after `base:`; that path is the `[WORK_DIR]` of the implementer (and of its fixer), which commits there. A rerun reuses the worktree. A task with no node `Test:` path never runs in a worktree: the landing verifies a task by running its plan `Test:` files with `node --test`, so `task-open --worktree` refuses it (exit 3, with an `Error:` line, before anything is written) when the plan gives it no `Test:` path, a `Test:` path that is not a `.mjs`, `.js` or `.cjs` file, a glob, or a path outside the repository; such a task runs sequentially, in the main checkout, once every earlier task is done or dropped. A coordinator task is always a main-checkout task: it starts only once every earlier task of the phase is done or dropped, whether the main session or the orchestrator runs it, and `task-open` refuses it (exit 3) while one is not.

**Review.** A worktree task is reviewed like any task, on its own head: `task-prep PLAN_FILE N --head <sha>`, with `<sha>` the tip of its branch (`git rev-parse wt/<plan stem>-t<N>`; without `--head`, `task-prep` takes that tip itself when the branch exists, as `task-close` does, and never `HEAD` of the main checkout), and `--fix-round --head <sha>` for each fix round; the review package, the reviewers and the saved outputs are the task's as always. The implementer's tracking entry is stamped with its worktree commit, which is gone after the landing; the review entry `task-close` writes names the landed sha, so the record still reaches the landed commit.

**Landing comes first.** `task-close` for a worktree task is called only after every earlier task of the phase has landed: a worktree task lands in plan order, and one that finished early waits. A call made early is refused (exit 3) with no `Error:` line: it is a wait, not a failure. `task-close PLAN_FILE N` (`--head <sha>` defaults to the tip of the task's branch, and a `--head` that is not that tip is refused with exit 3: the close removes the branch, and the commits after the reviewed one would go with it) needs the main checkout on the active phase branch with a clean tracked tree. With the task's BASE as merge base it folds the task's commits onto the current phase tip with `git merge-tree --write-tree` and `git commit-tree` (ONE commit on the phase tip, with the first commit's message and author; no hook runs), moves the phase branch to it with `git reset --keep`, appends `Landed: T<N> <sha>` and `Prep: T<N> r<R> <landed sha>` when the attempt has a `Prep:` line, runs the task's plan `Test:` files with `node --test` at that tip and appends `Tested: T<N> <sha>`. Only then come the `done --commit <landed sha>` move, the complete line, the record and the entry, and the worktree and its branch are removed (`git worktree remove --force` once no tracked file of the worktree has uncommitted changes, `git branch -D`), with a check that `git worktree list` no longer shows it. The test run is cut off after `TRIQUAL_LANDING_TEST_TIMEOUT_MS` milliseconds (default 600000; a value that is not a positive number of milliseconds is exit 2 before anything is written), a timeout is a failure and takes the undo below, and its output is `<workspace>/task-<N>-landing-test.log`; a `Test:` file that is not there fails, so a run of zero files is never a pass. A worktree task that made no commit lands nothing and closes at the tip of the phase branch (its complete line reads `<tip>..<tip>`, so a Phase check reopen squashes from that tip and never folds in the tasks that closed after the task opened), never at its own BASE and never at the main checkout's `HEAD`.

**Conflict or failing verification.** A merge conflict or a failing `Test:` file at the landing is undone, never patched: `git reset --keep` back to the previous tip; the two ledger lines `BASE: T<N> <previous tip>` and `Task <N>: landing conflict — re-run sequential`, in one write; the file `<workspace>/task-<N>-undone`, which dates the undone attempt (the gate, spec and hunter outputs older than it are never counted); `triqual tasks rework` when opted in; and the worktree and its branch removed. `task-close` ends in exit 3 with an `Error:` line. The orchestrator then runs the task again sequentially, in the main checkout: `task-open PLAN_FILE N` without `--worktree` and a fresh implementer from the brief (the undone attempt's commits went with its worktree). The ledger of the re-run starts after the undo line, so it starts again at round 1: the `Prep:` lines, fix rounds and `Budget:` line before it are not counted. An undo that was cut short (the process died after the reset, with or without its ledger lines written) is finished by the next call: a rerun of `task-close` finishes the clean-up (the two ledger lines when they are missing, the marker, the task moved back, the worktree and its branch removed) and exits 3 again, with the message that says so; it can finish an undo that died before its ledger lines only for a landing with no `Tested:` line whose parent is the phase tip, and otherwise the owner decides (see Refusals). After an undo `task-close` refuses the task (exit 3, with an `Error:` line) until its sequential re-run has a `Prep:` line: the worktree and its branch are gone, so a close before that would squash no commit and mark the task done with none of its work.

**A rerun after the landing.** A landing that stands (a `Landed:` line with no later `BASE:` line of the task) is never made again: the closed commit is the landed sha, whatever `--head` says, and `task-close` repeats only what is left. A crash can leave a landing half done, so it is trusted after two checks: its sha must still be on the phase branch, and its `Test:` files must have passed (`Tested: T<N> <sha>`; a rerun without it runs them again at the phase tip, and a failure is undone). A landing that is neither tested nor the phase tip cannot be tested again and is refused.

**Refusals.** Every exit-3 refusal of `task-close` writes its `Error: task-close T<N> — exit 3 — <cause>` line except the earlier-task wait and the linked-worktree refusal: a linked worktree (`run from the main checkout`) is refused before the workspace is known, so there is no ledger to write to, and the wait writes none because nothing failed; the wait is the refusal whose message starts `T<N> waits for`. These each write one: not on the active phase branch (or a detached HEAD), the tree is not clean, a `Test:` path that is a glob or outside the repository, and the other refusals of step 6. Two of them do not clear by a rerun: the landed commit is not on the phase branch (an undo cut short that the rerun cannot finish, see above), and a landing that is neither tested nor the phase tip is no longer the tip. They are errors the steps cannot resolve, so the orchestrator returns `BLOCKED` and the owner decides (both messages end by pointing here). To abandon the landing the main session takes the sha the owner names (the phase tip from before the landing) and does what the undo above does, in this order: it moves the phase branch to that sha (`git reset --keep <sha>` from the main checkout; nothing to do when it is already there); it writes `BASE: T<N> <sha>` and `Task <N>: landing conflict — re-run sequential` in one write; it creates the file `<workspace>/task-<N>-undone` (the sha and a newline); it removes the task's worktree and its branch (`git worktree remove --force`, `git branch -D wt/<plan stem>-t<N>`); and it runs `triqual tasks rework T<N> --plan <plan>` when opted in. The task then runs again sequentially. A bare `BASE:` line is not enough: without the line and the marker the re-run's record would count the undone attempt's fix rounds and its stale reviewer and hunter outputs.

**Stops and resume.** On a stop, a task that is reviewed but waits to land gets `Task <N>: awaiting landing` and keeps its worktree; a stop never removes one. A resumed phase reads the running tasks from the ledger (a task with a `BASE:` line and no complete line) and from `git worktree list`: `task-open PLAN_FILE N --worktree` again reuses a running task's worktree, a task with a `Landed:` line that no later `BASE:` line undid is closed with `task-close`, a task whose landing was undone (a `Task <N>: landing conflict — re-run sequential` line after its `Landed:` line) is re-run sequentially with `task-open` and no `--worktree` and is never closed before its re-run has a `Prep:` line, and the landing order holds as before.
